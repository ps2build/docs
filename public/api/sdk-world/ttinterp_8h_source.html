274#ifdef TT_SUPPORT_SUBPIXEL_HINTING_MINIMAL
275 /*
276 * FreeType supports ClearType-like hinting of TrueType fonts through
277 * the version 40 interpreter. This is achieved through several hacks
278 * in the base (v35) interpreter, as detailed below.
279 *
280 * ClearType is an umbrella term for several rendering techniques
281 * employed by Microsoft's various GUI and rendering toolkit
282 * implementations, most importantly: subpixel rendering for using the
283 * RGB subpixels of LCDs to approximately triple the perceived
284 * resolution on the x-axis and subpixel hinting for positioning stems
285 * on subpixel borders. TrueType programming is explicit, i.e., fonts
286 * must be programmed to take advantage of ClearType's possibilities.
287 *
288 * When ClearType was introduced, it seemed unlikely that all fonts
289 * would be reprogrammed, so Microsoft decided to implement a backward
290 * compatibility mode. It employs several simple to complicated
291 * assumptions and tricks, many of them font-dependent, that modify the
292 * interpretation of the bytecode contained in these fonts to retrofit
293 * them into a ClearType-y look. The quality of the results varies.
294 * Most (web)fonts that were released since then have come to rely on
295 * these hacks to render correctly, even some of Microsoft's flagship
296 * fonts (e.g., Calibri, Cambria, Segoe UI).
297 *
298 * FreeType's minimal subpixel hinting code (interpreter version 40)
299 * employs a small list of font-agnostic hacks loosely based on the
300 * public information available on Microsoft's compatibility mode[2].
301 * The focus is on modern (web)fonts rather than legacy fonts that were
302 * made for monochrome rendering. It will not match ClearType rendering
303 * exactly. Unlike the `Infinality' code (interpreter version 38) that
304 * came before, it will not try to toggle hacks for specific fonts for
305 * performance and complexity reasons. It will fall back to version 35
306 * behavior for tricky fonts[1] or when monochrome rendering is
307 * requested.
308 *
309 * Major hacks
310 *
311 * - Any point movement on the x axis is ignored (cf. `Direct_Move' and
312 * `Direct_Move_X'). This has the smallest code footprint and single
313 * biggest effect. The ClearType way to increase resolution is
314 * supersampling the x axis, the FreeType way is ignoring instructions
315 * on the x axis, which gives the same result in the majority of
316 * cases.
317 *
318 * - Points are not moved post-IUP (neither on the x nor on the y axis),
319 * except the x component of diagonal moves post-IUP (cf.
320 * `Direct_Move', `Direct_Move_Y', `Move_Zp2_Point'). Post-IUP
321 * changes are commonly used to `fix' pixel patterns which has little
322 * use outside monochrome rendering.
323 *
324 * - SHPIX and DELTAP don't execute unless moving a composite on the
325 * y axis or moving a previously y touched point. SHPIX additionally
326 * denies movement on the x axis (cf. `Ins_SHPIX' and `Ins_DELTAP').
327 * Both instructions are commonly used to `fix' pixel patterns for
328 * monochrome or Windows's GDI rendering but make little sense for
329 * FreeType rendering. Both can distort the outline. See [2] for
330 * details.
331 *
332 * - The hdmx table and modifications to phantom points are ignored.
333 * Bearings and advance widths remain unchanged (except rounding them
334 * outside the interpreter!), cf. `compute_glyph_metrics' and
335 * `TT_Hint_Glyph'. Letting non-native-ClearType fonts modify spacing
336 * might mess up spacing.
337 *
338 * Minor hacks
339 *
340 * - FLIPRGON, FLIPRGOFF, and FLIPPT don't execute post-IUP. This
341 * prevents dents in e.g. Arial-Regular's `D' and `G' glyphs at
342 * various sizes.
343 *
344 * (Post-IUP is the state after both IUP[x] and IUP[y] have been
345 * executed.)
346 *
347 * The best results are achieved for fonts that were from the outset
348 * designed with ClearType in mind, meaning they leave the x axis mostly
349 * alone and don't mess with the `final' outline to produce more
350 * pleasing pixel patterns. The harder the designer tried to produce
351 * very specific patterns (`superhinting') for pre-ClearType-displays,
352 * the worse the results.
353 *
354 * Microsoft defines a way to turn off backward compatibility and
355 * interpret instructions as before (called `native ClearType')[2][3].
356 * The font designer then regains full control and is responsible for
357 * making the font work correctly with ClearType without any
358 * hand-holding by the interpreter or rasterizer[4]. The v40
359 * interpreter assumes backward compatibility by default, which can be
360 * turned off the same way by executing the following in the control
361 * program (cf. `Ins_INSTCTRL').
362 *
363 * #PUSH 4,3
364 * INSTCTRL[]
365 *
366 * [1] Tricky fonts as FreeType defines them rely on the bytecode
367 * interpreter to display correctly. Hacks can interfere with them,
368 * so they get treated like native ClearType fonts (v40 with
369 * backward compatibility turned off). Cf. `TT_RunIns'.
370 *
371 * [2] Proposed by Microsoft's Greg Hitchcock in
372 * https://www.microsoft.com/typography/cleartype/truetypecleartype.aspx
373 *
374 * [3] Beat Stamm describes it in more detail:
375 * http://rastertragedy.com/RTRCh4.htm#Sec12.
376 *
377 * [4] The list of `native ClearType' fonts is small at the time of this
378 * writing; I found the following on a Windows 10 Update 1511
379 * installation: Constantia, Corbel, Sitka, Malgun Gothic, Microsoft
380 * JhengHei (Bold and UI Bold), Microsoft YaHei (Bold and UI Bold),
381 * SimSun, NSimSun, and Yu Gothic.
382 *
383 */
384
385 /* Activate backward compatibility (bit 2) and track IUP (bits 0-1). */
386 /* If this is zero, it means that the interpreter is either in v35 */
387 /* or in native ClearType mode. */
