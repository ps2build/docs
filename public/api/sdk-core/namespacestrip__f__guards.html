Detailed Description

Strip F_<name> compile-time guard pairs from a ps2sdk kernel source
file, leaving the body unconditional and leaving every OTHER conditional
(__OPTIMIZE_SIZE__, USE_KMODE, etc.) completely untouched - including
ones nested INSIDE an F_ block, which lose their enclosing guard but keep
their own.

Recognizes several guard spellings, all equally real - found the hard
way, not up front: an initial pass over kernel.S/sifcmd.c/etc only
handled #1 below, and go test/the golden-file suite had no way to notice
#2/#3 being silently left as real (always-false, since no F_ macro is
ever -D'd anymore) conditionals - loadfile.c's ~14 functions
(SifLoadModule and friends) got compiled to nothing, zero errors, only
found by grepping every already-stripped file for leftover "F_" text and
checking each hit by hand. #4 was found the exact same way, in a
completely different codebase (gsKit, not ps2sdk):
  1. #ifdef F_<name>                                  - kernel.S, most files
  2. #if defined(F_<name>)                             - loadfile.c, exclusively
  3. #if defined(F_A) || defined(F_B) [|| ...]          - sjis.c, guards shared
     data used by multiple F_-gated functions (e.g. a lookup table both
     isSpecialSJIS and isSpecialASCII need) - once every one of those F_
     names' own guards are gone, the shared data must always be kept too,
     so this form strips exactly like #1/#2. A #if mixing an F_ name with
     any NON-F_ condition is a real structural case this pattern doesn't
     predict and is left alone, matching the #else/#elif refusal below.
  4. #if F_<name>  (bare, no ifdef/defined())          - gsKit's ee/gs/*.c
     almost exclusively use this spelling instead of #1/#2 - works because
     an undefined identifier in a preprocessor #if evaluates to 0, making
     it functionally identical to #ifdef whenever nothing ever defines the
     symbol to anything but 0/1. Also has a compound form (bare terms
     joined by ||), handled the same all-F_-only-or-refuse way as #3.

Stack-based: every #if/#ifdef/#ifndef pushes a marker noting whether it's
an F_ guard (any of the 3 forms above) or not. Every #endif pops the
matching marker.

A bare F_ guard (#ifdef F_X ... #endif, no #else) has its two guard lines
dropped, body kept. A small number of F_ guards DO have a real #else -
inspected by hand (osd_config.c: converttobcd/convertfrombcd/
__adjustTime) and confirmed to be the same recurring shape every time:
the #ifdef branch is the real definition, the #else branch is JUST an
`extern` forward-declaration stub, needed only so some OTHER F_-gated
function in the same file compiling in isolation still has a prototype
for this one. Once every function compiles together in one pass, that
stub is redundant - the real definition from its own #ifdef branch
already provides both the declaration and the implementation to
everything below it in the same file. So for an F_ guard WITH an #else:
keep the #ifdef branch's body, drop the #else branch and its content
entirely. An #elif on an F_ guard has never been observed and stays a
hard refusal - a real structural surprise this pattern doesn't predict,
worth a human look rather than a guess.

Function Documentation

◆ _is_f_guard()

_is_f_guard ( stripped_line)
protected 
Returns True if stripped_line is any of the 5 recognized F_ guard
forms. A compound form requires EVERY "||" operand to name an F_
symbol (either bare or defined(...)) - a mixed condition (an F_ name
alongside something else) does not match, by design.

Form 4, bare "#if F_<name>" (no ifdef, no defined()), was found in
gsKit (ee/gs/src/*.c almost exclusively use this spelling, not the
ps2sdk-style #ifdef/defined() forms) - it works because an undefined
identifier in a preprocessor #if expression evaluates to 0, so
"#if F_gsKit_vram_alloc" is functionally identical to
"#ifdef F_gsKit_vram_alloc" whenever nothing ever defines it as
anything other than 0/1. A 4th real-world spelling of the exact same
ps2dev-community compile-once-per-function convention, found the same
way the first 3 were: grepping leftover F_ text after a first strip
pass looked clean by the OLD recognized-forms list.
